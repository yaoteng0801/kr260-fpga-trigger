Scope and boundaries

Version 1 deliberately closes the fixed-threshold trigger loop

Implemented in this project

  • Read HT and score02 from HDF5
  • Define reproducible float-to-unsigned-fixed conversion
  • Transfer events into the PL through AXI DMA
  • Evaluate HT, AD, and total trigger decisions in parallel
  • DMA results back and compare exactly against NumPy
  • Provide one-command UART control and a PYNQ backend

Intentionally outside the V1 PL

HDF5 parsing, threshold policy, file I/O, performance reporting, truth efficiency, and adaptive threshold control remain in software.

Not yet a 40 MHz online system

The PL runs at 100 MHz with trigger II=1, but DMA currently runs at its natural burst rate without a dedicated 40 MHz stream pacer.

Trigger algorithm

The PL compares both thresholds every cycle and returns four interpretable status bits

ht_pass = ht_q > ht_cut_q
ad_pass = ad_q > ad_cut_q
total_pass = ht_pass OR ad_pass

Comparisons are unsigned and strictly greater-than. Equality does not pass, exactly matching the notebook and NumPy golden model.

Output bitMeaning
0ht_pass
1ad_pass
2total_pass
3Input TKEEP != 0xff error
[31:4]Always zero
The result reports both the overall decision and its source: HT, anomaly score, or both.

AXI4-Stream correctness

An elastic output register preserves data and packet boundaries under backpressure

s_axis_tready =
    ~m_axis_tvalid
    | m_axis_tready

A new event is accepted whenever the output register is empty or the downstream consumes the current result.

Throughput

Without stalls, one event enters and exits every clock: initiation interval = 1.

Stall behavior

When the downstream is not ready, TDATA/TKEEP/TLAST/TVALID remain stable until the handshake completes.

Packet boundaries

DMA asserts TLAST at each chunk boundary; the trigger propagates it to the matching result, including one-event and partial-tail packets.

Bitstream strategy

Two bitstreams isolate DMA validation from trigger execution

kr260_loopback.bit

64-bit MM2S connects directly to 64-bit S2MM.

  • Isolates DMA, DDR, and cache issues
  • Contains no threshold logic
  • Used by menu action 2

kr260_trigger.bit

64-bit inputs pass through trigger RTL and produce 32-bit results.

  • Uses fixed MMIO addresses
  • Used by menu actions 3/4/5
  • Remains loaded after full verification

PYNQ integration

Fixed-address Bitstream mode bypasses the board's xclbinutil failure

Verified loading sequence

  1. Set Clocks.fclk0_mhz = 100.0
  2. Load the .bit with Bitstream(...).download()
  3. Create DMA/trigger MMIO mappings at fixed addresses
  4. Use allocate() for physically contiguous I/O buffers
  5. Verify addresses are below 4 GiB for the 32-bit DMA address width

Why not Overlay?

The board's /usr/bin/xclbinutil segfaulted while synthesizing an XCLBIN from HWH metadata.

Compatibility path retained

--pynq-loader overlay remains available when xclbinutil works and the matching HWH is present.

Implementation quality and remaining risk

The core loop is verified; long-term online operation still needs targeted work

Completed

Reproducible Vivado flow; 100 MHz timing met; trigger uses 101 LUT / 147 FF; two bitstreams; PYNQ backend; UART menu; zero mismatches on real HDF5.

Engineering safeguards

DMA error/timeout checks, reset after timeout, S2MM-first ordering, threshold readback, buffer-address bounds, and context-managed cleanup.

Not yet verified

UIO/u-dma-buf on this board image, long-duration stress, thermal stability, interrupt mode, and controlled 40 MHz pacing.

Recommended next steps

  1. Add a stream pacer and test at 40 MHz
  2. Run long-duration and thermal stress tests
  3. Verify UIO or converge on one PYNQ deployment path
  4. Extend fixed cuts with a PS-side adaptive policy
