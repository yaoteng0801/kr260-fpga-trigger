The problem

Can a physics selection be reproduced exactly inside an FPGA?

For every event, decide whether its transverse activity or anomaly score is large enough to keep.

Starting point

An offline study provides HDF5 samples and a two-variable trigger rule.

Engineering question

Can the same rule run in programmable logic while Linux controls it and checks every returned result?

Scope

This is a trigger-path demonstrator—not yet a complete detector front end or a sustained 40 MHz system.

Physics decision

The trigger keeps an event if either observable exceeds its cut

Two event-level inputs

HT summarizes transverse activity in the event.

score02 is the anomaly-detection score supplied by the offline study.

keep = (H_T > 218.0)
    OR (score02 > 250.893)

One decision, with diagnostic information

Returned bitInterpretation
HT passThe HT cut fired
AD passThe anomaly-score cut fired
Total passAt least one cut fired
Format errorThe input byte mask was malformed

The comparison is strictly “greater than”; equality does not pass.

The FPGA implements the same transparent physics predicate as the software reference; it does not infer a new selection.
Sources: Trigger_io.tex · docs/EVENT_FORMAT.md03 / 13
The output deliberately retains which branch accepted the event. That makes the result interpretable: an accepted event can be attributed to HT, anomaly score, or both. [Sources] Trigger_io.tex; docs/EVENT_FORMAT.md.

Why Zynq?

One chip combines flexible software with deterministic event logic

Processing system · ARM

Prepare and supervise

  • Run Linux and Python
  • Read HDF5 files in manageable chunks
  • Load the FPGA bitstream and set thresholds
  • Move data through shared DDR
  • Compare FPGA results with the reference

Programmable logic · FPGA

Make the event decision

  • Accept a stream of compact event words
  • Compare HT and score02 in parallel
  • Produce one result for every input event
  • Preserve event and packet ordering under stalls
  • Operate independently of file formats

FPGA implementation

The PL reduces each event to two comparisons and one OR

One compact 64-bit word per event

[63:32] score02
fixed-point ×256
[31:0] HT
fixed-point ×2
ht_pass = ht_q > ht_cut_q
ad_pass = score_q > score_cut_q
keep    = ht_pass OR ad_pass

Why fixed point?

The ARM converts floating-point inputs with a documented rule. The FPGA then needs only unsigned integer comparators—small, fast, and reproducible.

Streaming behavior

An elastic register can accept one event per 100 MHz PL cycle when unstalled, while preserving packet boundaries under backpressure.

Runtime control

Two AXI-Lite registers hold the cuts; software writes and reads them back before DMA begins.

Sources: docs/EVENT_FORMAT.md · hw/rtl/axis_trigger_core.sv · hw/rtl/trigger_axi_lite_regs.sv06 / 13
The fixed-point conversion is part of the interface contract, not an undocumented approximation. Both software and hardware use the same quantized values, including the strict comparison boundary. [Sources] docs/EVENT_FORMAT.md; hw/rtl/axis_trigger_core.sv; software/trigger_format.py.

ARM and PYNQ software

The ARM turns stored events into a controlled FPGA experiment

01 · PREPARE

Read and encode

Read one HDF5 chunk, quantize both observables, and pack one word per event.

02 · CONFIGURE

Load and program

Load the bitstream, allocate buffers, write both cuts, and verify readback.

03 · EXECUTE

Transfer by DMA

Start the receiver first, send the input packet, and monitor completion and errors.

04 · VALIDATE

Compare every event

Calculate the same selection in NumPy and report any differing result.

Board-side application

Two FPGA images

A loopback image separates data-movement failures from trigger failures

kr260_loopback.bit

Returns each 64-bit input word without applying a trigger.

  • Tests DDR buffers and cache synchronization
  • Tests both DMA channels and packet boundaries
  • Answers: “Can data make a clean round trip?”

kr260_trigger.bit

Replaces the direct connection with the fixed-point trigger core.

  • Produces one 32-bit decision word per event
  • Uses thresholds programmed by the ARM
  • Answers: “Does the FPGA make the correct decision?”
loopback image → prove transport → trigger image → prove selection
Sources: hw/tcl/create_project.tcl · software/loopback_test.py · software/deterministic_trigger_test.py08 / 13
Using two images makes debugging causal. If loopback fails, the trigger algorithm is not yet under test. If loopback passes and the trigger result fails, attention can move to formatting, thresholds, or RTL logic. Hardware

  • Custom streaming trigger core and programmable registers
  • Trigger and diagnostic loopback bitstreams

Software

  • PYNQ bitstream, MMIO, and DMA-buffer backend
  • Bit-exact NumPy model and machine-readable reports

Validation strategy

Four test layers isolate transport, RTL behavior, and data agreement

A · TRANSPORT

DMA loopback

Send known words through DDR and DMA, then require an exact return.

B · RTL

Simulation

Exercise equality boundaries, stalls, byte masks, and packet endings.

C · DECISION

Synthetic events

Cover neither, HT only, anomaly only, both, and values exactly on each cut.

D · APPLICATION

Conclusion

The prototype connects a physics selection to verified FPGA execution

What has been demonstrated

  • The ARM transforms HDF5 observables into a documented event stream.
  • The FPGA applies programmable HT and anomaly-score cuts.
  • The complete board path returns bit-exact results on synthetic and real-file tests.

What should come next

  1. Add a controlled 40 MHz input pacer.
  2. Run long-duration and thermal tests.
  3. Measure physics acceptance and background rejection across threshold choices.
  4. Decide whether adaptive policy belongs on ARM or in later FPGA logic.
The main result is a trustworthy hardware–software bridge: the same event definition, the same cuts, and a verifiable decision for every tested event.
